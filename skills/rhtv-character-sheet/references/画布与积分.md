```

```

- 工程名在 `projects` 里，并且它的 `canvas_id` 就是参考图所在的画布：**情况一（工作台）**，看第一节。
- 不满足上面的条件（画布不是本机工作台建的，或者本机记录里没有这个工程）：**情况二（canvas.py）**，看第二节。

  - 例：病娇女教师画布 `2120368499697168386` 出图时不在本机记录里，走的是情况二。2026-11-12 复查时，这一行的人设图节点已经改成 `<工程>｜v<N>·人设图` 这种工作台式的名字（不带【通过】），位置也变了；它现在在不在本机工作台记录里**未验证**，照样以 `wb list` 为准。

### 2. 通用约定

| 项 | 值 |
|---|---|
| 模型 | `image-image-g-2-text-to-image`（G2 低价渠道版，图生图，最多 10 张参考图）。用户明确说过不换模型 |
| 参数 | `aspectRatio` 16:9，`resolution` 4k |
| 输入 | 整张生成时，`--left` 接参考图节点（同一角色多张参考图合成一个版本时，每张接一次，见第一节第 2 步）；局部修改时，`--left` 接上一张生成图的**节点 ID**（工作台里槽位名的限制见第一节第 9 步） |
| 怎么跑 | **一次只跑一个节点，按顺序跑**。两个节点并行跑时，有一个没派发成功过 |

| 提示词 | 一律写进 UTF-8 文件，用 `--prompt-file` 传，不要直接写在命令行里 |
| 路径 | 路径里有空格，一律加双引号 |

下文的简写（`<skills>` 指本 Skill 所在目录的上一级，本机是 `F:\BaiduSyncdisk\PI Agnet\.agents\skills`）：


### 3. 两条路共用的三条做法

**① 跑前报预估，说完就跑；问用户的事不阻塞跑图。**

- 建好节点后用 `cv estimate` 拿报价，告诉用户这轮跑几次、预计多少积分（口径见第三节），说完直接跑，不等回复（总则第五节）。情况一另有工作台 SKILL.md 第〇、六节的规定（在画布上跑生成不问用户），情况二没有这句，但总则第五节一样要求报完就跑，所以两条路做法相同。
- **要超出已报的预估时，分两种（总则第五节）**：
  - 正常迭代（多一次整图重出、多一次局部修改）：先在回复里说明原因和新增的次数、积分，说完就跑，不等回复。例如“比刚才报的多 1 次：v2 重出后只剩胸，局部改胸 1 次，约多 10 积分，现在跑”。用户中途改了需求、按新需求重出的，同样重新报一次再跑。
  - 因为修不动而继续加码：已经到了 `尺度自查.md` 1.4 要停下报用户的地步（局部修改也没解决），还想再试一次——不跑，停下把现状和可选方案（每个方案的次数、积分）报给用户定。
- **需要用户定的事不阻塞跑图（总则第三节）**：没有先例的小件颜色（黑鞋、黑腰带、手套等）、用户没说过的情况（半透面料、打底裤等），先按最贴近参考图的默认方案写提示词，照常报预估、照常跑；出图后在汇报里列进“需要你决定”。报预估那条回复里可以顺带一句“这几项我先按参考图出，你要别的说一声”，但不为等答复而不跑。也不在出图前替用户加遮挡（例如不预先给半透面料加衬里）；出图后透肤，自查记“临界（规则未定）”问用户。
- 要等用户答复才能动的只有这几件：删除节点（本节第 4 小节）；修不动之后还要继续花积分（上面第二种）；分不清哪几张参考图属于同一个版本、要不要合成一个版本（第一节第 2 步）——只等拿不准的那几张，能确定的版本照常先跑。

**② 拿到这一轮的图再裁切。** 下载、裁切之前要确认两件事：节点状态是 `finished`；输出图的 `url` 和上一轮不同。`cv status` 会自动查这两项：
- 生成节点只有 `ready: true`（`state: done`）时才下载、裁切；`ready: false` 时什么都不下载，原因写在 `warning` 里。不要绕过它，自己去下载节点上的图。
- 上一轮的旧图靠运行记录排除：`cv run` 每派发一个节点之前，先把节点上已有的图地址（`before_urls`）写进运行记录文件，写不进去就不派发。默认路径是 `%USERPROFILE%\.rhtv-character-sheet\runs.json`，`run` 的 `start` 行和 `status` 的输出里都有 `state_file`。用了 `--state-file` 的话，`run` 和 `status` 要给同一个文件。
- 节点不是本机 `cv run` 跑的（比如用 `wb run` 跑的，或者在网页上跑的），运行记录里就没有它，`status` 会给出 `note`。这个节点只跑过一次的话可以忽略；重跑过的话，加 `--exclude-url <上一轮的 url>` 再查。
- **节点用 `cv run` 跑过、之后又在 `cv run` 之外重跑过**（网页上点了运行、用 `wb run` 跑过）：运行记录只在 `cv run` 时更新，`status` 会拿上一次 `cv run` 记下的旧记录去排除，**不会给 `note`**，可能把上一次 `cv run` 的图当成这一轮的。这时查 `status` 一律加 `--exclude-url <上一轮的 url>`（更早几轮的图也可以各加一个 `--exclude-url`）。上一次 `cv run` 拿到的地址在 `status` 输出的 `last_run.url` 里；`ready: true` 的图正好等于 `last_run.url` 时，输出会带 `note` 提醒。
- `status` 只读画布，只往 `--out` 目录写图片和裁切图。

**③ 选修法和什么时候停下，按 `尺度自查.md` 1.4。** 整图重出还是直接局部修改、整图不收敛后怎么转、局部修改也解决不了时停下报用户，都只在那里写全，本文不重复。本文只管操作：整图重出的命令见第一节第 9 步、第二节第 7 步；局部修改见第一节第 9 步、第二节第 8 步；修不动之后还要不要继续花积分，见本小节①。不提议换模型（总则第三节）。

### 4. 删除口径（两条路一样，依据总则第六节）

- **能删的前提**：用户有明确指示（例如“只留合格的”“删掉旧图”“替换掉”），或者明确同意。用户“打回”或说“不合格”，不等于同意删除。
- **删之前**：在回复里列出要删的每个节点的名字和 ID。
  - 用户已经给了明确指示：列出来以后就可以删，删完报告删了哪些。
  - 没有明确指示：列出来问用户，等用户明确同意再删。
- 指示或同意只管当时那一批节点。之后新出现的废稿，要重新确认。
- 拿不准算不算“合格”的图（比如标了临界、等用户定的那几张）既不当作过审，也不当作废稿删掉，先问用户。
- **工作台命令自动删节点，也要先确认**：`wb adopt`、`wb put` 放进已经有节点的槽位时，会直接删掉槽位里的旧节点（wb.py 里直接调 `node delete`，不提示）；`wb remove` 会删掉槽位里的节点。跑这几条命令之前，先满足上面的前提，并在回复里列出会被删掉的旧节点名和 ID。工作台 SKILL.md 第六节第 5 步写的是“没被采用的生成节点直接删”，人设图这一步以本条为准（总则第六节）。
- **永远不删**：用户放的参考图和其他上传图、文字卡（包括工作台的标题卡和总览）。`cv delete` 会拒绝删除没有模型的节点，并在 `refused` 里列出来。用户坚持要删，请用户自己在画布上手动删。
- 回复模板：
  > v1–v4 已确认。画布上还有这些没过审的生成节点，删掉后每列只留过审图：
  > - `<节点名>`（`<节点ID>`）
  > - …
  > 参考图和文字卡不删。

  有明确指示时，接一句“按你说的只留合格的，现在删”，然后删；没有指示时，接一句“可以删吗？”，等回复。

## 一、情况一：工程在工作台记录里

生成、采用、记账都走 wb（总则第六节）。在工作台里，**节点命名、状态标记和列位都由 wb 管**：不要手动改名，也不要用 `cv update` 挪槽位里的节点（下次 wb 重排时会被挪回标准位置）。状态从节点名就能看出来：

| 状态 | 节点名 | 位置（wb 自动摆） |
|---|---|---|
| 生成中（包括还在自查、审核，没有 adopt） | `<工程>｜生成·<tag>`，例如 `<工程>｜生成·v1人设图` | 本行上方的临时区（行 y − 2600） |
| 待审核（自查和两个独立审核都做完，`adopt --review` 之后；临界项修不动的也标待审核，汇报里写明临界） | `<工程>｜v1·人设图·<造型>【待审核】` | v1 列第一格 |
| 打回 | `<工程>｜v1·人设图·<造型>【打回】` | 不动 |
| 通过 | `<工程>｜v1·人设图·<造型>`（去掉【待审核】，不另外加【通过】） | 不动 |

跑之前报预估，说完就跑（第〇节第 3 小节①）。

### 1. 开工

```
wb list
wb stage <工程> 03 进行中
```

`wb list` 返回的 `canvas_id` 是画布 ID；`slots` 列出已有的 `v<N>·人设图`；`defaults.image_model` 是默认模型。

### 2. 找参考图节点

- 参考图已经拖到画布上该工程那一行：
  ```
  cv refs --canvas <canvas_id> --out "<工程目录>\03_人设图\参考图"
  ```
  `kind=上传图` 就是用户放上来的图。同一行（同一个 `group`）里按 x 从左到右排，依次对应 v1、v2……对不上就问用户。下载下来的原图用来写人设的头部和服装；看全图时打开 `<节点ID>_s.jpg` 缩略图更快。上传图超过 20 张时，脚本不下载，要加 `--group <分组>` 或 `--node <ID>` 指定。工程的分组 ID 在本地 `<工程目录>\工作台.json` 的 `group` 字段里，只读，不要手改。
- **同一角色有多张参考图**（例如正面 + 背面、全身 + 头部特写）：按用户指定合成一个版本（总则第六节）。
  - 哪几张合成一个版本、各部分（服装、头部等）以哪张为准，按用户说的；拿不准几张图是不是同一个角色、要不要合成，先问用户，只等这几张，能确定的版本照常先跑（第〇节第 3 小节①）。
  - 合成后一个版本一列：`wb gen` 的 `--left` 把这几张参考图各接一次（G2 最多 10 张），`adopt --version N` 照常，版本号按合成后的版本数从左到右排。工作台 SKILL.md 第五节写的“版本数 = 用户给的参考图张数”，合成时以用户指定为准。
  - 参考图节点不在工作台记录里，wb 不会挪它们，合成后这几张参考图照原样留在画布上。
  - 派审核员时，这个版本的 `ref` 写成数组（`审核员.md` 第 2 节）。
  - 多张参考图一起输入时的出图效果（例如模型会不会把几张图的服装混在一起、`--left` 的先后顺序有没有影响）**未验证**。
- 参考图只在本地 `<工程目录>\03_人设图\参考图\` 里、画布上没有：`--left` 只能接画布节点，要先把图上传到画布。wb.py 的 `put` 内部用的写法是 `wb rh upload <名字> -p <canvas_id> -f <文件> -t image`（**本 Skill 没有实测过**）。上传后用 `cv refs` 确认节点 ID。也可以请用户把图拖到画布上那一行。

### 3. 建节点（每个版本一个）

```
wb gen <工程> --type image --prompt-file prompt_v1.txt --left <参考图节点ID> --model image-image-g-2-text-to-image --set aspectRatio=16:9 --set resolution=4k --tag v1人设图
```

- 返回的 `node` 就是节点 ID。节点名和位置见本节开头的表，不用手动改。
- wb 会核对画布上保存的提示词。比文件短会给 `warnings`，要转告用户并核对。
- `--set aspectRatio=16:9` 这种不带引号的写法是工作台文档的写法，**本 Skill 没有实测**；canvas.py 实测过的写法是 `aspectRatio="16:9"`。建好后读回参数核对一次：
  `wb rh node get id:<节点> -p <canvas_id> --include params`，看比例是 16:9、分辨率是 4k。

### 4. 跑前报预估

```
cv estimate --canvas <canvas_id> --node <节点1> --node <节点2>
```

按第三节的口径给用户报一句预估，说完就跑。

### 5. 跑（一次一个）

```
wb run <工程> --node <节点>
```

- `ok:true`：已经按报价记账（报价 × 100 = 积分）。报价为 0、用了免费额度或报价不完整时，会记成“未核对”：画布名末尾带 `+`，标题卡花费后面写“（含未报价项）”。
- `pending:true`（退出码 4）：这时**已经按报价记了账**。用 `wb wait <工程> --node <节点>` 接着等。**不要换 ID 重跑，也不要先 adopt。** `wb wait` 最后报失败的，账本里这一条的状态会改成 `failed_check_refund`，但记的积分不会自动扣回，要到账单页核对后补记（第 11 步）。
- `ok:false`：没记账。把 `errorMessage` 和 `code` 原文告诉用户，不要自动重试。
- 一个节点返回了再跑下一个，不要写后台循环一次派发一批。如果一定要写循环脚本，按第四节的做法加 STOP 检查。
- 重出一律用 `wb gen` 新建节点，**不要对同一个节点再跑一次 `wb run`**：`wb wait` 和 `wb adopt` 只看节点有没有产物，分不出上一轮的旧图。

### 6. 下载并裁切，做自查（先不要 adopt）

`wb run` 不下载图片，`wb adopt --review` 会马上把图标成【待审核】并放进槽位。所以要先下载、自查、审核，都通过了再 adopt：

```
cv status --canvas <canvas_id> --node <节点> --tag v1r1 --crop --out <自查目录>
```

- 先看输出：`status` 是 `finished`、`ready` 是 `true`，才说明拿到了这一轮的图，这时脚本已经把图下载成 `<自查目录>\v1r1.png`，并调用 `scripts/crops.py` 裁出 8 张自查图。`ready` 是 `false` 时什么都没下载，按 `warning` 处理（第〇节第 3 小节②）。
- 再核对 `url` 和上一轮自查用的图不同。工作台里每一轮都是新节点，`url` 本来就不同；如果相同，说明查错了节点。
- `wb run` 跑的节点，本机运行记录里没有，输出里会有 `note`，新节点可以忽略。
- `crops.files` 按 0 到 7 的顺序给出路径，直接交给审核员用。`crops.info` 里写的如果是“退回四等分”，要先看 0全图，确认裁切位置对不对。

### 7. 收进槽位

```
wb adopt <工程> 人设图 --node <节点> --version 1 --label <造型> --review
```

- 这条命令会做几件事：下载图到 `<工程目录>\03_人设图\v1_人设图.png`（同名旧文件挪进 `_旧版\`）；把节点改名为 `<工程>｜v1·人设图·<造型>【待审核】`；把节点摆进 v1 列第一格（列里从上到下是 人设图 → 母版 → 包装）；刷新标题卡和总览。
- **槽位里原来已经有节点时，adopt 会自动删掉旧节点。** 先按第〇节第 4 小节的删除口径办：用户已经明确说过替换旧图、删掉旧图或只留合格的，就在回复里列出将被删掉的旧节点名和 ID，然后 adopt；否则先列出来问用户，同意后再 adopt。用户不同意删旧图时，先不 adopt，新图留在临时区（名字还是 `生成·…`），把新旧两张都给用户看，等用户定。
- 参考图节点不在工作台记录里，wb 不会挪它，也不会删它。
- 所有版本都 adopt 完了再停下，把画布链接和每张图哪条过、哪条临界、哪条没过告诉用户（格式见 `审核员.md` 第 7 节；总则第四节）。同时：
  - 参考图上没有的东西逐项列出，每项标明“有意加”（为擦边、人设或红线加的）还是“模型自己加”（提示词没写、模型画出来的）（总则第三节“新增要透明”）。
  - 模型自己加的：主体服装上的黑色单品必须去掉（违反只改黑色）；其他的列进“需要你决定”，或者下一轮点名去掉。不要因此直接判服装项不过，也不要默认保留。
  - 按默认方案先出的事（没有先例的小件颜色、用户没说过的情况）、临界项、两个审核员意见相左的项，都列进“需要你决定”（第〇节第 3 小节①）。

### 8. 用户反馈

- 通过：`wb approve <工程>`。名字由 wb 改（去掉【待审核】）。看输出：`still_waiting` 和 `still_rejected` 都是空、`state` 变成“通过”，03 的审核点才算全过；之后按第 10–12 步收尾。
- 打回：把用户原话写进 UTF-8 文件，然后 `wb reject <工程> v1·人设图 --note-file 原话.txt`，再按第 9 步重出或局部修改。
- 部分通过：先 `reject` 没过的那几张，再 `approve`。

### 9. 重出整图和局部修改

- 整图重出还是局部修改、什么时候停下报用户：按 `尺度自查.md` 1.4（第〇节第 3 小节③）。
- 重出整图：写新提示词文件，`wb gen … --left <参考图节点ID> --tag v1人设图r2` 建一个新节点，然后按 run → status --crop 自查 → 审核 → adopt 的顺序走。
- 局部修改（以上一张生成图为输入，只改局部，提示词见 `提示词模板.md`）：
  ```
  wb gen <工程> --type image --prompt-file fix_v2.txt --left <上一张生成图的节点ID> --model image-image-g-2-text-to-image --set aspectRatio=16:9 --set resolution=4k --tag v2人设图改胸
  wb run <工程> --node <新节点>
  cv status --canvas <canvas_id> --node <新节点> --tag v2fix --crop --out <自查目录>
  ```
  - **`--left` 写节点 ID。** 槽位名（如 `v2·人设图`）只有 adopt 之后才有，指向的是槽位里那张已经 adopt 的图。要改的图还在自查、审核阶段（没 adopt）时，写槽位名要么报错（槽位还不存在），要么接到槽位里的旧图上。只有要改的正好是槽位里那张已 adopt 的图（比如用户打回后在它的基础上改），才可以写槽位名。
  - 自查时所有项目都要重新查一遍，审核过了再 `wb adopt <工程> 人设图 --node <新节点> --version 2 --label <造型> --review`。这一步会删掉槽位里的旧节点，按第 7 步的删除确认办。

### 10. 用户确认后清理

1. 列出这一行的图片节点：`cv refs --canvas <canvas_id> --group <分组> --no-download`。`kind=生成节点`、名字是 `<工程>｜生成·…`、又不在 `wb list` 的 `slots` 里的，就是没被采用的生成节点。
2. 按第〇节第 4 小节的删除口径列出、确认，然后删：
   ```
   cv delete --canvas <canvas_id> --node <ID1> --node <ID2> --yes
   ```
   `cv delete` 会拒绝删除参考图和上传图，优先用它；也可以用 `wb rh node delete id:<节点> -p <canvas_id>`。
3. 已经收进槽位的节点，不要用 `node delete` 删。要删掉整个版本，用 `wb remove <工程> v3`（本地文件会挪进 `_旧版\`），同样要先按删除口径确认。
4. 参考图、标题卡、总览不删。
5. 删完再跑一次第 1 条的 `cv refs` 核对。

### 11. 核对积分并补记

报价为 0 或不完整的那几次，`wb run` 已经先按报价记了账（报价 0 就记 0），并标成未核对：画布名末尾带 `+`，这个工程的标题卡花费后面写“（含未报价项）”。到账单页核对（第三节）后补记：

```
wb cost --name <工程> --add <差额积分> --settled
```

以下结论来自读 wb.py（VERSION 0.4.0）的 `cmd_cost`，没有实跑：
- 差额 = 账单模型行实际扣的积分 − wb 已经按报价记的积分。差额是负数（例如报价记了 10、账单确认没扣）时写成 `--add=-10`；`--add -10` 按 argparse 的规则一般也能识别，两种写法都没实测。
- **差额是 0 也要写 `--add 0`**：`cmd_cost` 只有给了 `--add`（0 也算）才会处理 `--settled`。只写 `wb cost --name <工程> --settled` 什么都不改，`+` 还在。`--add 0 --settled` 会在账本里记一笔 0 积分的手工条目，然后清掉未核对标记、同步画布名和总览。
- `--settled` 清两样东西：
  - 这个工程的未核对标记（必须带 `--name`），标题卡的“（含未报价项）”随之去掉；
  - **整张画布**的未核对标记，也就是画布名的 `+`。这是整个周期共用的一个标记，脚本不会再看其他工程有没有没核对的运行。同一张画布上别的工程还有没核对的运行时，加 `--settled` 也会把 `+` 去掉。
- 所以：这张画布上所有带未核对的运行都核对完了，最后一次补记才加 `--settled`；还有没核对的，补记差额时先不加。哪些工程还没核对，看各工程标题卡有没有“（含未报价项）”，或者本地 `<工程目录>\工作台.json` 的 `incomplete` 字段（只读，不要手改）。
- 不带 `--name` 时只改画布合计和画布名的 `+`，不改工程的花费和标记，所以补记一律带 `--name`。
- 看账本：`wb cost --name <工程>` 输出这张画布账本的最近 10 条（整张画布的，不按工程筛；不带 `--add`、`--sync` 时不改画布，只把本地账本原样存回）。`wb run` 记的条目有 `time`、`project`、`node`、`amount`、`task`（taskId）、`status`，核对账单时按这些对。

### 12. 03 收尾：不用 `wb stage <工程> 03 完成`

- wb.py 的写法是 `wb stage <工程> <阶段> <状态>`：阶段写编号（`03`），按 `01 文案`…`07 复盘` 的前缀匹配；状态是任意文字，脚本不校验，写什么就把什么写进标题卡和总览。工作台没有“完成”这个状态。
- 03 的收尾就是第 8 步的 `wb approve`：没有待审核、打回的槽位时，它会自动把状态改成“通过”。再按第 10、11 步清理画布、核对积分。
- 进 04 是工作台的事：按工作台 SKILL.md 第四节“通过 / 可以”那一行，本阶段最后一个审核点通过后执行 `wb stage <工程> 04 进行中`，接着按工作台第五节做母版视频。`stage` 换到另一个阶段时，会把轮次重置为 1、清掉标题卡上的最近意见。

## 二、情况二：画布不在工作台记录里（`scripts/canvas.py`）

跑之前报预估，说完就跑，和情况一一样（第〇节第 3 小节①）。

### 1. 脚本说明

canvas.py 会按自己所在的位置找同级目录里的 `rhtv-workbench/scripts/wb.py`，然后 import 它，通过 `wb.rh()` 调用 rhtvcli。找不到时会报错，并列出找过的路径；这时可以设环境变量 `RHTV_WORKBENCH_SCRIPTS`，指向 wb.py 所在的目录。

| 子命令 | 作用 | 会不会写画布、扣积分 |
|---|---|---|
| `refs` | 列出图片节点，按分组、x、y 排序，`kind` 标成上传图或生成节点；把上传图下载到 `--out`（默认 `.\refs`），每张附一张 `_s.jpg` 缩略图；`--no-download` 只列不下载 | 不写画布 |
| `create` | 建 G2 节点，但不运行；建完读回提示词长度、比例、分辨率（`saved`），并附上报价（`estimate`） | 写画布，不扣积分 |
| `estimate` | 报价换算成积分，标出哪些用了免费额度 | 不写画布 |
| `run` | 按顺序跑；每跑一个之前检查 STOP 文件，并把节点上已有的图写进运行记录文件（写不进去就不派发）；打印 `taskId` 和 `url`；`--download` 下载图片，`--crop` 下载并裁切 | **扣积分** |
| `status` | 查节点状态（`status` 就是节点的 data.status）和这一轮的输出图；生成节点只有 `finished` 且有排除旧图后的新图时，`--download`/`--crop` 才会下载、裁切；`--exclude-url` 手动指定要排除的旧图 | 不写画布 |
| `update` | 改名（`--name`）、挪位（`--x --y`，两个一起给）、换提示词（`--prompt-file`） | 写画布 |
| `delete` | 删除生成节点。不加 `--yes` 时只列清单（退出码 2）；没有模型的节点一律拒绝删除 | 写画布 |

退出码：0 成功；1 有失败；2 `delete` 没加 `--yes`；4 `run`/`status` 有节点还没拿到这一轮的图。

### 2. 读画布，定列位

```
cv refs --canvas <画布ID> --out <工作目录>\refs
```

`kind=上传图` 就是用户放上来的参考图（也可能是别的上传图，要结合位置和名字判断）。同一行里按 x 从左到右排，依次是 v1、v2……对不上就问用户。每张参考图的 `node`、`x`、`y`、`h`、`group` 都要记下来。

同一角色有多张参考图时，按用户指定合成一个版本，拿不准就问，只等拿不准的那几张（和第一节第 2 步相同）。合成后这几张算一列：`cv create` 的 `--left` 每张给一次（最多 10 个），后面版本的序号按合成后的列数往后排。列位见下一小节。

### 3. 列位布局

```
            v1 列            v2 列            v3 列 …
y ≈ 38    [参考图 v1]      [参考图 v2]      [参考图 v3]     ← 用户放的，不动
y = 960   [v1 人设图]      [v2 人设图]      [v3 人设图]     ← 正式位置
y = 1240  [v1 局部修改/备选]                                ← 临时位置
y = 1520  [同一列第二个临时节点]
```

- 列的 x 等于这个版本参考图节点的 x，直接用 `refs` 输出的 x（已经取整）。
- 人设图放在 y=960。如果参考图底边（y + h）超过 960，就把人设图放到参考图下方不重叠的位置。间距素材里没定，可以参照工作台列内间距 `gap_y=50`。
- 一个版本合成了多张参考图时：列 x 取这几张里最左边那张的 x；上一条的“参考图底边”取这几张里底边（y + h）最大的那张；人设图不要压到下一个版本的列上（节点宽 360）。合成版本的摆法素材里没有先例（**未验证**）：用户指定了位置就按用户的；没指定就先这样摆、照常跑，在汇报里问用户要不要挪（挪用 `cv update --x --y`）。
- 局部修改或备选节点放在同一列 y=1240，再多一个就放 y=1520。
- 新节点都放进这一行的分组：`create` 时加 `--group <参考图的 group>`。
- G2 16:9 的生成节点在画布上默认显示成 360×203，不用改尺寸。
- 实例：病娇女教师画布 `2120368499697168386`，分组 `group_5c22c5bcf42d4e09f50ea02d`，出图时的列 x 是 v1 1755、v2 2403、v3 3005、v4 3587。这张画布后来被重排过，现在的坐标以 `refs` 为准，这组数只当格式参考。

### 4. 命名和状态

| 什么时候 | 节点名 |
|---|---|
| 刚建、在跑、正在自查或审核 | `<工程名>｜v<N>·人设图【生成中】` |
| 自查和两个独立审核都做完 | `<工程名>｜v<N>·人设图【待审核】` |
| 用户确认 | `<工程名>｜v<N>·人设图【通过】` |
| 局部修改的临时节点 | `<工程名>｜v<N>·人设图·改胸【生成中】`（后缀写这次改了什么） |

改名用 `cv update --canvas <画布ID> --node <ID> --name "<新名>"`。名字里有全角的 `｜` 和 `【】`，在 PowerShell 里要用双引号把整个名字包起来。

### 5. 建节点，报预估

```
cv create --canvas 2120368499697168386 --group group_5c22c5bcf42d4e09f50ea02d --name "261111-JP-病娇女教师｜v2·人设图【生成中】" --prompt-file prompt_v2.txt --left node_1794395495579_sk1q0si --x 2403 --y 960
```

- 返回 `node`。`saved.warning` 出现时表示画布上保存的提示词比文件短，要核对。`saved.aspectRatio` 和 `saved.resolution` 是读回来的参数值，读不到时为 null。
- 其他可选参数：`--left` 可以给多次（最多 10 个）；`--model`、`--aspect`、`--resolution` 默认分别是 G2 低价版、16:9、4k；`--no-estimate` 表示不报价。
- 所有节点都建好后，一起报预估（口径见第三节），说完就跑：
  ```
  cv estimate --canvas <画布ID> --node <A> --node <B> --node <C>
  ```

### 6. 跑

```
cv run --canvas <画布ID> --node <A> --node <B> --tag v2r1 --tag v3r1 --crop --out <自查目录>
```

- 最好在前台跑（每个节点默认最多等 600 秒，用 `--timeout` 改）。要放到后台跑，就必须先把 `start` 那一行里的 `pid`、`stop_file`、`state_file` 和 `started_at` 记下来（停批量时要用，见第四节）。
- 每个节点会依次输出 `dispatch` 一行，然后是 `done`、`failed` 或 `pending` 中的一行。`done` 那一行带 `taskId`、`url`、`file` 和 `crops`（`crops.files` 按 0 到 7 排好序，直接交给审核员）。最后一行 `summary` 汇总 done、failed、pending、not_dispatched、`estimate_points` 和 `free_quota_runs`。
- `done` 的条件：节点状态是 `finished`，并且有跑之前没有的新图。同一个节点重跑时，节点上只有跑之前就有的图，会判为 `pending`，不会把旧图当成新结果。
- `failed`：不要自动重试，把 `errorMessage` 和 `code` 原文告诉用户。带 `dispatched: false` 的是跑之前就读不到节点、根本没派发，不扣分。
- `stopped` 行带 `error`（运行记录读写失败）：后面的节点都没派发，不扣分。把 `error` 告诉用户；修好记录文件，或者换一个 `--state-file` 再跑（之后的 `status` 也要用同一个文件）。
- `pending`：**不要换 ID 重跑**，已经派发出去的任务会扣积分。过一会儿用下面的命令查：
  ```
  cv status --canvas <画布ID> --node <ID> --tag v2r1 --crop --out <自查目录>
  ```
  **裁切前先确认 `status` 是 `finished`、`url` 和上一轮不同。** 脚本已经替你查了：`ready: true` 才会下载和裁切；`ready: false` 时什么都没下载，按 `warning` 等一会儿再查（第〇节第 3 小节②）。
- `--tag` 是每个节点下载和裁切时用的文件名前缀，个数要和 `--node` 一样，按顺序对应。每一轮用不同的 tag（r1、r2、fix），本地才能留下每一轮的图。

### 7. 重出整图

整图重出还是局部修改、什么时候停下报用户：按 `尺度自查.md` 1.4（第〇节第 3 小节③）。整图重出用同一个节点，换提示词再跑：

```
cv update --canvas <画布ID> --node <ID> --prompt-file prompt_v2_r2.txt --name "<工程名>｜v2·人设图【生成中】"
cv run --canvas <画布ID> --node <ID> --tag v2r2 --crop --out <自查目录>
```

- `cv run` 会自动记下上一轮的图，`done` 和之后的 `cv status` 都会排除它。
- **上一轮不是用本机 `cv run` 跑的**，查 `status` 一律加 `--exclude-url <上一轮的 url>`。包括两种：运行记录里根本没有这个节点（`status` 会给 `note`）；节点用 `cv run` 跑过、之后又在网页上或用 `wb run` 重跑过（运行记录是旧的，`status` **不会**提示，详见第〇节第 3 小节②）。上一次 `cv run` 的图地址在 `status` 输出的 `last_run.url` 里。
- 为什么情况二沿用同一个节点、情况一每次 `wb gen` 新建节点：`cv run`/`cv status` 能用运行记录分出新旧图，`wb wait`/`wb adopt` 分不出（第一节第 5 步）。
- 旧图会不会留在节点的输出历史里**没有验证过**（2026-11-12 查过一个已完成节点，输出里只有一张图，但不知道它重跑过没有），靠本地按 tag 保存的图留底。

### 8. 局部修改，以及收尾

```
cv create --canvas <画布ID> --group <分组> --name "<工程名>｜v4·人设图·改胸【生成中】" --prompt-file fix_v4.txt --left <上一张生成节点ID> --x 3587 --y 1240
cv run --canvas <画布ID> --node <新节点> --tag v4fix --crop --out <自查目录>
```

- `--left` 接的是**上一张生成图的节点**，不是参考图。
- 自查时所有项目都要重新查一遍（总则第四节），自查和两个独立审核都做完后改名为【待审核】（临界项修不动的也一样，汇报里写明临界），交给用户。汇报内容和情况一相同（第一节第 7 步最后一条）。
- 用户确认这张局部修改图之后，按下面的顺序收尾（先删后挪，避免两个节点叠在 y=960）：
  1. 被替换的旧整图节点按第〇节第 4 小节的删除口径处理：在回复里列出它的名字和 ID；用户说过“替换”“只留合格的”这类话就直接删，没说过就先问。删除命令：`cv delete --canvas <画布ID> --node <旧节点> --yes`；
  2. `cv update --canvas <画布ID> --node <改图节点> --name "<工程名>｜v4·人设图【通过】" --x 3587 --y 960`。
  用户不同意删除的话，改图节点就留在 y=1240，问用户怎么摆。

### 9. 用户确认后清理（画布上只留过审图）

1. 先列出这一行的节点：`cv refs --canvas <画布ID> --group <分组> --no-download`。
2. 每列只留用户确认的那张图，改名为【通过】，并放在 y=960。这一行里其他 `kind=生成节点` 的人设图节点就是要删的（拿不准算不算合格的，先问）。
3. 按第〇节第 4 小节的删除口径和回复模板列出、确认，然后删：`cv delete --canvas <画布ID> --node <ID1> --node <ID2> --yes`。
4. 再跑一次 `cv refs … --no-download` 核对：每列应该只剩参考图和一张【通过】的人设图。

脚本的保护：
- 不加 `--yes` 时，脚本只列清单（退出码 2），不会删。删除口径的前提没满足之前，不要加 `--yes`。
- 没有模型的节点（参考图、上传图、文字卡），脚本一律拒绝删除，会在 `refused` 里列出来。

## 三、积分

### 1. 换算和两种口径

- `node estimate` 只给人民币（CNY）报价。按 1 元 = 100 积分换算。G2 低价版报价 0.1 元/次，也就是 10 积分/次（账单实测）。
- 用了免费额度时报价为 0（`usedFreeLimit`）：canvas.py 会输出 `free_quota: true`；wb run 会标成未核对，画布名末尾带 `+`。**报价 0 不等于没花钱。**
- 两种口径分开写，不要混在一个数里：
  - **单价口径**：次数 × 10 积分。不管有没有用免费额度，都按单价算。
  - **报价合计口径**：`cv estimate` 的 `total_points`，是每个节点当前报价换算后加起来。报价为 0（免费额度）的节点按 0 计入，`free_quota_count` 给出有几个这样的节点。
  - 有节点用了免费额度时，两个数会不一样。
  - 有节点报价失败时（`cv estimate` 的 `failed` 不为空、退出码 1），`total_points` 没算这些节点，不能拿它当合计报给用户，改按单价口径报，并说明哪几个节点报价失败。
- 命令行查不到余额，也查不到实际扣了多少积分，只能去网站账单页看。

### 2. 跑前报预估

跑之前告诉用户，说完就跑，例如：
> 这轮跑 3 次（v2、v4 各整图重出 1 次，v3 局部修改 1 次）。按单价 10 积分/次，共约 30 积分；`cv estimate` 报价合计 20 积分，因为其中 1 次报价为 0，走免费额度。实际扣分以账单为准，跑完核对。

要超出已报的预估时，按第〇节第 3 小节①（总则第五节）：
- 正常迭代（多一次重出或局部修改）：先说明原因和新增积分，说完就跑。例如“比刚才报的多 1 次：v4 重出后只剩胸，局部改胸 1 次，约多 10 积分，现在跑”。
- 因为修不动而继续加码：停下让用户定，不跑。
- 跑之前不知道、事后才发现的超出（停批量没停干净多派发了；用户中途改需求时已经派发出去的任务）：没法先说，跑完如实告诉用户多了几次、多少积分、为什么。

需要用户定的事（没有先例的小件颜色等）不影响这条：照常报预估、照常跑，在汇报里列进“需要你决定”（第〇节第 3 小节①）。

### 3. 跑后到账单页核对

- 账单页：https://www.runninghub.cn/bill-task（任务与账单）。
- 怎么看：**每次生成在账单里有两行**。“Canvas-<画布ID>”那一行是 0 积分，旁边写模型名的那一行才是实际扣的积分。按时间段对上这一轮跑的次数，只把模型行的积分加起来。
- 内置浏览器已经登录 RH 时，可以打开页面读取文字（读页面文本或用 JS 读）。没登录就请用户自己登录或自己看；不要替用户输入账号密码。
- 账单里一行对应哪次运行：按时间对。canvas.py 的运行记录 `runs.json` 里有每个节点最近一次的 `dispatched_at`、`checked_at`、`taskId`（同一个节点只留最近一次）；工作台看 `wb cost --name <工程>` 输出的账本条目 `time`、`task`。账单行上能不能看到 taskId、能不能按 taskId 对上，**未验证**。
- 工作台工程：核对后用 `wb cost --name <工程> --add <差额积分> --settled` 补记，`--add 0`、负数和 `--settled` 的用法见第一节第 11 步。

**模型行扣 0 时，先分清是免费额度还是别的原因。** 只有成功的运行才能说成免费额度：
- 先看这次运行成没成功：
  - canvas.py：`run` 的 `done` 行，或 `status` 的 `state: done` 是成功；`failed` 行或 `state: failed` 是失败；`failed` 行带 `dispatched: false` 的根本没派发，账单里不该有它。
  - 工作台：`wb run` 返回 `ok:true`，或 `wb wait` 返回 `ok:true` 是成功；`wb run` 直接返回 `ok:false` 是失败（没记账）；`wb wait` 最后报失败的也是失败（已经按报价记了账，账本状态 `failed_check_refund`）。
- **成功的运行，模型行扣 0**：
  - 跑之前的报价就是免费额度：说成免费额度。怎么看：`cv estimate`（或 `cv create` 附带的报价）里这个节点 `free_quota: true`；canvas.py `run` 的 `dispatch` 行 `free_quota: true`、`summary` 的 `free_quota_runs`。工作台跑前第 4 步的 `cv estimate` 就有这一项；`wb run` 的 warning 不区分“报价为 0”和“报价不完整”，不能单靠它判断。
  - 跑之前报价不是 0（例如 10 积分），账单模型行却是 0：原因不明，不要说成免费额度。按账单记（以账单为准，总则第五节），对用户如实说“这次报价 10 积分，账单模型行显示 0，原因没核实”。
- **失败的运行**：不算免费额度，也不算进成功的次数，单独说：“另有 K 次运行失败（错误原文……），账单里这几次显示扣了 X 积分”。失败会不会扣积分、会不会退款、退款在账单里显示成什么样，**都未验证**，按账单模型行实际显示的记。工作台里 `failed_check_refund` 的那几次已经按报价记过账，账单确认没扣的，用负数差额冲掉（第一节第 11 步）。
- 跟用户这样说：
  - 核对过：“跑了 N 次，按报价 X 积分，账单核对实际扣了 Y 积分”。
  - 成功的运行、跑前报价是免费额度、模型行确认扣 0：“其中 K 次走免费额度，账单确认这 K 次没扣积分”。整轮都是这样时：“跑了 N 次，都走免费额度，账单确认没扣积分”。
  - 有失败的：在上面的话后面单独加一句失败的次数和账单显示的积分。
  - 还没核对：“实际扣分还没核对”。
  - **永远不说“花费 0”。**

## 四、停批量

正确做法：
1. **软停（首选）**：在 `start` 那一行给出的 `stop_file` 路径上建一个 STOP 文件：
   ```
   New-Item -ItemType File "<stop_file 的路径>"
   ```
   当前节点跑完后，脚本不会再派发下一个，并输出 `stopped` 和 `not_dispatched`。
2. **硬停**：`Stop-Process -Id <pid>`，pid 也在 `start` 那一行里。已经派发出去的那个节点，服务器上还是会跑完并扣积分。不知道 pid 的话，用这条命令找出命令行里带 `canvas.py run` 的 python 进程：
   ```
   Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Select-Object ProcessId, CommandLine
   ```
3. **确认真的停了**：
   - 再查一遍进程，确认没有 `canvas.py run` 还在运行。
   - 用 `cv status` 查这一批里还没出 `done`/`failed` 行的节点（软停时就是 `not_dispatched` 里的；硬停没有 `summary`，要按 `start` 行的 `nodes` 逐个查）。`cv run` 派发前一定先写运行记录：`last_run.dispatched_at` 早于 `start` 行的 `started_at`、或者没有 `last_run` 的，是没派发；晚于 `started_at` 的，按已派发处理（会扣积分），等它跑完再查。
   - 之后去账单页看，确认没有多出来的模型行。
4. 下一批开跑之前，先删掉 STOP 文件。STOP 文件还在时，`run` 会拒绝启动。

不要这样做：
- **用 TaskStop 停后台的 PowerShell 不够**：PowerShell 里启动的 python 子进程不会停，会把剩下的节点跑完。病娇女教师案例因此白扣了 20 积分。
- 多个节点并行派发。一律按顺序跑。
- 工作台里 `wb run` 一次只跑一个节点，本身不用 STOP 文件，要停就是不再调用下一个 `wb run`。如果自己写了循环脚本来调 `wb run`，必须照 canvas.py 的做法，每跑一个之前先检查 STOP 文件。

## 五、报错速查

| 现象 | 处理 |
|---|---|
| `INSTALLED_RELEASE_CHANGED` | 在 Git Bash 里跑了，换成 PowerShell |
| canvas.py 报“没找到 rhtv-workbench 的 scripts/wb.py” | 两个 Skill 不在同一个 skills 目录下。装好 rhtv-workbench，或者设 `RHTV_WORKBENCH_SCRIPTS` |
| 报“没找到 rhtvcli” | rhTV 客户端没装或没登录，按 rhtv-workbench 的 `references/安装与登录.md` 处理 |
| `saved.warning` 或 wb gen 的 warnings 提示提示词变短 | 去核对画布上保存的提示词；提示词必须通过文件传 |
| estimate 的 `failed` 不为空（例如 `MODEL_INPUT_REQUIRED`） | `total_points` 没算这些节点，按单价口径报预估，把 `code` 原文告诉用户。`MODEL_INPUT_REQUIRED` 先查节点的输入图（`--left`）有没有接上（**未验证**） |
| run 返回 pending | 不要换 ID 重跑。情况一用 `wb wait`，情况二用 `cv status` |
| run 返回 failed | 把原文告诉用户，不要自动重试 |
| run 的 `stopped` 行带 `error`（运行记录读写失败） | 没有派发，不扣分。修好记录文件，或换 `--state-file`（`status` 用同一个） |
| status 的 `warning`：状态不是 finished | 还在跑，过一会儿再查；没下载、没裁切 |
| status 的 `warning`：只有上一轮的旧图 | 这一轮的图还没出来，过一会儿再查 |
| status 的 `state: failed` | 节点运行失败：把 `errorMessage` 原文告诉用户，不要自动重试 |
| status 的 `note`：本机运行记录里没有这个节点 | 节点只跑过一次就忽略；重跑过就加 `--exclude-url <上一轮的 url>` 再查 |
| 节点用 `cv run` 跑过，之后又在网页上或用 `wb run` 重跑过 | 运行记录是旧的，status **不会**给提示：查 status 一律加 `--exclude-url <上一轮的 url>`；上一次 `cv run` 的图在输出的 `last_run.url` 里 |
| status 的 `note`：这张就是上次 cv run 拿到的图 | 节点之后没在 `cv run` 之外重跑过，就忽略；重跑过，就加 `--exclude-url <这个地址>` 再查 |
| status 的 `state: unknown` 或 `state_file_error` | 记录文件读不了，或者多张图分不出新旧：用 `--exclude-url` 排除旧图后再查 |
| delete 退出码 2 | 没加 `--yes`。删除口径的前提满足了吗（第〇节第 4 小节） |
| delete 的 `refused` 不为空 | 要删的是参考图或上传图：不删；用户坚持就请他自己手动删 |
| `crops.error` 或 `crops.info` 显示退回四等分 | 看 0全图 判断；不对就手动跑 `python "<skills>\rhtv-character-sheet\scripts\crops.py" <图> <输出目录> <标签> --cuts x1,x2,x3` |
